Your AI Assistant Doesn't Understand Your Codebase. Here's the Fix That Lives Inside Your Repo.

A look at Draft's knowledge graph engine — deterministic codebase understanding for AI assistants, with no MCP server, no SaaS, no API key, no leaked code.

The Bottom Line

Most "AI for code" tools improve context by sending more of your code to a third party — vector DBs, MCP servers, indexing services, hosted retrieval pipelines. Draft's graph engine takes the opposite path: a local, live-queried knowledge graph of your repo, powered by codebase-memory-mcp — a local engine Draft installs — that indexes your repo and answers structural queries on demand.

No external service. No cloud. No network call. No API key. Your AI assistant gets sharper context because the structural truth of your codebase — modules, dependencies, hotspots, call edges, proto APIs — is queried live from the engine running locally alongside your code.

Why "Better Context" Usually Means "More Cloud"

Walk through the standard playbook for giving an LLM context on a large codebase:

  1. Stand up a vector database.
  2. Pick an embedding model (and pay per token to index your repo).
  3. Run a chunker, hope the chunk boundaries respect function scopes.
  4. Wire an MCP server or hosted retrieval API.
  5. Re-index on every meaningful change.
  6. Pray the semantic search returns the right five files for the prompt.

Every step adds latency, cost, a vendor, a secret to manage, and a question about where your proprietary code now lives. And the output is still probabilistic — "files that look similar to your query" is not the same as "files that actually call this function."

For regulated environments (finance, healthcare, defense, on-prem GPU clusters), most of this isn't even allowed.

What Draft Does Instead

Draft installs codebase-memory-mcp, a single-binary engine (tree-sitter + LSP across 159 languages, 100% local). You run it once during /draft:init or /draft:graph to index the repo. From that point on, skills and shell helpers query the engine live — no snapshot files committed, no data going stale between commits:

draft/graph/
└── schema.yaml              # gate marker: engine metadata, counts
                             # (access: engine-live — all other data queried from engine)

The engine holds the graph. draft/graph/schema.yaml is the only committed artifact — a tiny gate marker that confirms the engine has indexed the repo and records provenance counts. All structural queries go directly to the engine at call time.

Five Properties That Change How AI Reasons About Your Code

1. Deterministic, Not Probabilistic

A vector search asks "which chunks look semantically related?" The graph answers "which functions actually call buildGoIndex?" — by name, with file paths and line numbers.

graph-callers --symbol buildGoIndex

Output:

{
  "symbol": "buildGoIndex",
  "callers": [{"name": "...", "file": "..."}],
  "source": "memory-graph"
}

The AI no longer guesses. It reads a fact.

2. Zero External Services

Vector DB (Pinecone, Weaviate, pgvector)None
Cloud embedding API (OpenAI, Voyage, Cohere)None (local only)
MCP server / hosted retrievalNone
Re-indexing pipelineIncremental, git-aware (built in)
Per-token indexing cost$0

The graph engine is one local process reading your source files.

3. Always-Fresh, Never-Stale Context

Because the graph is queried live from the local engine rather than read from a committed snapshot, it is always current. Every query re-indexes incrementally first — about a tenth of a second when nothing changed — so it reflects edits made seconds ago, uncommitted ones included. There is no refresh step to remember.

Committed snapshots went stale on the very next commit and duplicated what the engine already serves precisely on demand. The engine-only model eliminates that entire class of drift.

4. Blast-Radius Queries Before You Edit

Before changing a file, ask the graph what depends on it:

graph-impact --file auth/auth.h

You get back:

{
  "target": "auth/auth.h",
  "kind": "file",
  "impacted": [{"name": "...", "file": "...", "qualified": "...", "hop": 1}],
  "downstream_files": ["..."],
  "affected_modules": ["auth", "api", "tests"],
  "max_depth": 3,
  "by_category": {"code": 31, "test": 12},
  "status": "ok",
  "truncated": false,
  "source": "memory-graph"
}

The AI assistant — and you — now know exactly how many tests to update, which docs go stale, which configs ship the change. No "I think this might be safe."

5. Hotspots and Cycles, Cheaply

hotspot-rank --top 10                  # symbols ranked by fan-in
cycle-detect                           # circular call dependencies
mermaid-from-graph --diagram module-deps   # ready-to-paste architecture diagrams

This is the kind of thing teams used to commission a consultant to produce as a PDF. It now runs in seconds, on every commit, for free, locally.

How the AI Actually Uses This

Draft's skills (/draft:implement, /draft:review, /draft:bughunt, /draft:debug, /draft:decompose) are wired to call the graph during context loading. Concretely:

  • /draft:implement queries impact + hotspots before writing a plan, so the proposed change lists every test and downstream file by name.
  • /draft:review pulls call edges and module dependencies to flag changes that touch hub modules or break module boundaries.
  • /draft:bughunt walks call edges to widen the search radius around a suspect function, deterministically, without spraying tokens at unrelated files.
  • /draft:debug uses callers + impact to scope the investigation rather than asking the LLM to grep.

When the graph engine has not indexed the repo, every skill degrades silently — the graph enriches reasoning, it never gates it.

What This Means for the Three People Reading This

If you're an engineer: stop pasting whole repos into a chat window. A 30-second /draft:graph produces a context layer your AI assistant can actually navigate, and it costs nothing per query.

If you're an engineering leader: the graph is your audit trail for AI-assisted changes. Every PR can show which structural relationships shifted. No vendor lock-in, no data egress, no compliance review for a new SaaS.

If you work in a regulated or air-gapped environment: this is the entire point. The graph runs on a laptop, on a build agent, on a DGX node behind a firewall. Code never leaves the box. Your AI workflow finally has a context strategy that legal will sign off on.

The Larger Argument

The industry default for "AI + code" is to bolt more cloud onto your repo. Draft's bet is the opposite: the artifact that makes AI useful on a codebase is a deterministic structural index served by a local engine running alongside the code, refreshable in seconds, queryable on demand, readable by humans and machines alike.

Embeddings have a place. Vector search has a place. Hosted retrieval has a place. But for the question every AI assistant actually asks — "what does this code touch, and what touches it?" — the right answer is a graph, queried live from a local engine running on your machine, under your control.

Try It

# Install Draft (Claude Code plugin)
npx @drafthq/draft install claude-code

cd your-repo
/draft:init                                 # indexes the repo via codebase-memory-mcp

# Or refresh the index at any time:
/draft:graph                                 # re-index after major refactors

# Query the live engine via shell helpers:
scripts/tools/hotspot-rank.sh --top 10
scripts/tools/graph-impact.sh --file path/to/file

The engine runs locally, indexes your repo, and answers queries on demand. No committed snapshot files, no staleness — your AI assistant just got a lot less guessy.
